# NTTドコモ ハッカソン 2026

6人チームで、5日間のプログラムのうちハッカソンに充てられた3日間（2〜4日目）に、現在地の周辺に絞った地域SNSアプリを作ったときの記録である。
自分が担当した範囲と、そこで下した判断を残している。

| 項目 | 内容 |
|---|---|
| 主催 | 株式会社NTTドコモ（インターンシップ） |
| 期間 | 2026年9月7日〜10日（1〜4日目、オンライン）、9月14日（5日目、対面。座談会と懇親会） |
| 形式 | 6人チーム。1〜2日目にアイデアソン、2〜4日目にハッカソン（4日目の正午に提出）、4日目に最終発表（プレゼン10分+質疑10分） |
| テーマ | 「すべての人が豊かさを感じられる世界をめざして新しいサービスを創る」 |
| 成果物 | 現在地の周辺に絞った地域SNSアプリ（Flutter + Node.js）とデモ |
| 自分の担当 | フォロー・公開範囲、店舗情報の紐づけ、地図の部品、テスト |

## 課題設定

**ペルソナ**: 大学院1年・理系・郊外で一人暮らし。移動は徒歩と自転車で、行動範囲は半径3km程度。
決めるのが面倒で、友人と集合しても行き先が40分決まらず、結局いつもの店に落ち着く。

**課題**: 近所に住んで数年経つと「街の全部を知っている」つもりになり、遊びも食事もワンパターン化する。
地図アプリは情報が多すぎて結局いつもの店に戻り、写真中心のSNSは近所の気軽な場所選びには向かない。

**解決策**: 現在地から5km以内の投稿だけを地図とタイムラインに出す地域SNS。
情報量を絞ることで、近所の知らなかった場所に行き着けるようにする。

## アイデアソンからの経緯

1. チーム各自の困りごと6件（雨、食事のマンネリ、メール見逃し、生活リズム、お金、遊び）を出し合い、4案に整理
2. 審査員の中間フィードバックを経て、災害時の行動支援案と地域SNS案の2案に絞り込み
3. 両案を評価軸（課題の解像度・独創性・3日で動くか）で点数化し、地域SNS案に決定

審査員から繰り返し指摘されたのは次の2点で、これが設計の軸になった。

- 投稿型サービスは良い情報が集まらないと利用者が増えない。情報を提供してもらう仕組みを具体化すること
- 既存の地図アプリや写真SNSと何が違うかを、根拠付きで言えること

## 自分が担当した範囲

一人分のブランチにまとめて実装し、プルリクエストでチームに取り込んだ。

| 項目 | 数 |
|---|---|
| チームに取り込んだ変更 | 68ファイル、約5,800行の追加（注） |
| 提出時点で単独で書いたファイル（このリポジトリに収録） | 42。補助実装やハッカソン後の改良を含めた収録の内訳は [source/README.md](source/README.md) にある |
| テスト | 56件（バックエンド30、フロントエンド26）。ハッカソン後の改良分93件を含めると収録分は149件 |
| ハッカソン後に足した改良 | ログインとセッション、踏破率の API、フォロー関係の保存の DynamoDB 版（それぞれテストつき） |

（注）チームの非公開リポジトリに出した自分のプルリクエストの規模である。元のリポジトリが非公開のため、この数字はこのリポジトリからは確認できない。

**機能**

- ユーザーとフォロー機能。リクエスト承認制の鍵アカウントを含む公開範囲の制御
- 投稿・コメントの削除（※）、プロフィール写真
- 投稿場所と店・施設の紐づけ。周辺候補の取得、場所検索、住所の逆引き
  - Google のキーが無いときは OpenStreetMap に切り替える。Overpass の公開サーバーは混雑や利用制限で応答しないことがあるため、3つのサーバーへ同時に問い合わせて最初に成功した結果を使い、すべて失敗したときだけ Nominatim で最寄りの1件を返す
  - 公開サーバーに負荷をかけないよう、OpenStreetMap への問い合わせは1本ずつ間隔を空けて行い、同じ地点の結果は15分キャッシュする
- 地図の5km円、現在地表示、店ごとのピン、直近の投稿を強調する表示（※）

※ 本体は他のメンバーと共同で編集したファイルにあるため、このリポジトリには収録していない。
地図の表示は地図画面（`map_screen.dart`）が本体である。
収録しているのは、削除のときに画像ファイルを消す処理（`upload.ts`）と、地図で使う部品
（現在地アイコン、強調表示用の炎のアイコン、ピンを押したときのカード）およびそのテストである。

**品質と安全性**

- テスト56件（バックエンド30件、フロントエンド26件）
- 地図APIキーをソースに書かず、バージョン管理の外から読み込む形にした（バックエンドは `.env` を読んで環境変数に入れる）
- JSON保存の同時書き込み対策と、エラー応答の形式をJSONに統一

## 技術構成

| 層 | 採用したもの | 理由 |
|---|---|---|
| フロントエンド | Flutter（Dart） | 1つのコードでAndroidとWebの両方にデモを出せる |
| バックエンド | Node.js + TypeScript + Express | 型がつく。3日で書き切れる範囲に収まる |
| 保存 | JSONファイル | デモの規模ではDBを立てる手間に見合わない。スキーマは後で移せる形にした |
| 地図 | Google Maps | 現在地と周辺施設の検索を1つのSDKで賄える |
| 店・施設の検索（バックエンド） | Google Places API。キーが無いときは OpenStreetMap（Overpass API と Nominatim）。住所の逆引きは常に Nominatim | Google のキーを設定していない環境でも、周辺候補の取得と場所検索が動く |

**やらないと決めたこと**: 自分の担当分を取り込んだチームの main では、認証基盤、クラウド配置、管理画面、CI/CD を入れていない。
3日で動くデモに映らないものは作らないと決め、その判断をチームのリポジトリの README に明記した。

**チームが別のブランチで進めたもの**: 別のメンバーが、Firebase Authentication によるログインと、
AWS（DynamoDB と S3）へのデータと画像の保存を、別のブランチで統合した。最終発表ではこの構成も使っている。
統合そのものは自分の実装ではない。自分が関わったのは、この構成を動かす中で AWS を呼び出す部分のコードを修正したことと、
AWS の管理画面で保存されたデータを確認・操作したことである。この修正はコミットしていないため、
このリポジトリにもチームのリポジトリにも残っていない。

ハッカソン後に、チームが採用した構成（DynamoDB）に合わせて、自分の担当分であるフォロー関係（鍵アカウントの承認制を含む）の
保存を DynamoDB に移せるようにした。チームのブランチのコードは使わず、キー設計から作り直している。
テストは偽物のクライアントに対して通したうえで、自分の AWS アカウントにテーブルを作り、確認用スクリプトを実際の DynamoDB に流した。
二重リクエスト、二重の承認、取り消し後の承認が条件つき書き込みで失敗することを含む11段がすべて成功し、Scan は発行していない
（2026年9月22日。手順と結果は [source/backend/infra/README.md](source/backend/infra/README.md)）。

### 同時書き込みへの対処

保存をJSONファイルにした結果、同じファイルへの読み書きが重なると内容が壊れる問題が出た。
次の2段構えで対処している。

1. ファイルごとに直列化のキューを持ち、同じファイルへの操作を同時に走らせない
2. 書き込みは一時ファイルへ出してから本体と置き換える

2 は、開発サーバーやテストが同じファイルを読んでいる瞬間に置き換えが失敗することがある。
そこで少し待って再試行し、それでも駄目なら内容を直接書き込む形にした。
これは原子的ではないが、書き込みが失われるよりはましだという判断で、理由をコードのコメントに残している。

## 振り返り

**できたこと**

- 既存サービスとの差を根拠付きで説明し、想定質問と回答を文章でチームに共有した
- 自分の担当範囲にテストを書き、他のメンバーが触っても壊れたと分かる状態にした
- デモの都合で割り切った箇所に、なぜそうしたかを残した

**課題**

- 実装着手が3日目になった。2日目の時点で最小構成は決めていたので、その日のうちに縦に1本通せたはず
- 目的・前提・やらないことを先に固定しないまま議論を始め、同じ論点を繰り返した
- 前半は遠慮が先に立ち、実装以外の場面で貢献しきれなかった。メンターからも
  「技術的な貢献だけでなく、遠慮せず発言すべき」と指摘を受けた。
  強みで貢献するのは正しいが、それを理由に議論から引かない

## ハッカソン後に取り組んだこと

審査で受けた指摘のうち期間中に形にできなかったものと、発表のあとの振り返りで見つけた課題に取り組んだ。
提出時点のコードには手を入れず、`source/backend/src/improvements/` に分けてある。

| 指摘・課題 | 提出時点はどうだったか | 何をしたか |
|---|---|---|
| 投稿型のサービスは、良い情報が集まらないと利用者が増えない。情報を提供してもらう仕組みを具体化すること | 半径で絞って表示するだけで、投稿する動機を作る仕掛けがなかった | 踏破率を出し、「残り○か所は未訪問」を示して、埋めにいく理由を作った |
| 既存の地図アプリや写真SNSと何が違うかを、根拠付きで言えること | 口頭で説明するしかなく、数字がなかった | 半径ごとの候補数を並べ、絞ることで候補がどれだけ減るかを数字で出した |
| （発表後の振り返りで見つけた課題）操作者をクライアントの申告で受け取っており、誰でも他人を名乗れた | 公開範囲をサーバー側で判定していても、鍵アカウントが成り立っていなかった | ログインとセッションを入れ、身元をセッションから決めるようにした |
| （発表後の振り返りで見つけた課題）JSON 保存の同時書き込み対策はプロセスの中のキューで、サーバーを複数立てると守れない | フォロー関係も同じ JSON 保存に載っていた | フォロー関係の保存を interface に切り出し、DynamoDB 版を足した。同時書き込みは条件つき書き込みにして、保存先の側で守る |

詳細は [source/README.md](source/README.md#ハッカソン後に足したもの) にある。

## 今後の改善点

デモとして割り切った部分のうち、まだ残っているもの。

| 箇所 | 現状 | 本来やるべきこと |
|---|---|---|
| 保存 | フォロー関係は、ハッカソン後に DynamoDB 版を用意し、環境変数で切り替えられる（既定は JSON。実際の DynamoDB に対する確認まで済み）。利用者・投稿・ログイン情報は JSON ファイルのままで、直列化キューで同時書き込みを凌いでいる | JSON のままのデータは、複数プロセスや複数端末からの書き込みに対応できていない。同じように保存先を差し替えられる形にして移す。DynamoDB 版の利用者一覧は1人につき4回の問い合わせになるので、件数を利用者の側に持たせる |
| 地図APIキー | ソースには書かず、バージョン管理の外から読み込んでいる | 配布するアプリに鍵が入る以上、参照元の制限をかけないと漏れたときに止められない |
| テスト | 単体テスト149件（提出時56件、改良分93件） | フロントとバックエンドを繋いだ通しの確認は手動だった。自動で1本通すところまで用意したい |
| 自動化 | なし | テストが149件あるのに自動実行されていない。CIを入れれば、他のメンバーの変更で壊れたことにその場で気づける |

一番効くのは最後のCIだと考えている。テストを書くところまでは3日でもできたが、
それを回し続ける仕組みまで入れられなかった。
次に短期間のチーム開発をやるときは、初日にテストの自動実行だけ先に置く。

認証については、上の「ハッカソン後に取り組んだこと」で着手した。
